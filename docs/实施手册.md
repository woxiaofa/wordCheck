# 实施手册：从零到可用的小程序 MVP

> 本手册按"微信云开发 + Taro"路线编写。所有平台规则类内容都必须在动手前对照微信/腾讯云官方文档核实一遍——这类文档变动频繁，本手册不承诺时效性。
> 主要读者：懂前端、写过 Koa 后端的开发者。

## 一、技术选型（已定）

### 表 |
层 | 选择 | 理由 | 备选
后端 | **微信云开发云函数（Node.js）** | 免备案、免证书、免运维；云函数直接用 `OPENID` 登录 | 自建 Koa + 云数据库（等验证完商业模式再迁）
数据库 | **云开发数据库**（托管 MongoDB） | 与云函数同环境、零配置、免费额度够 MVP | 自建 MySQL/PostgreSQL（复杂查询场景才需要）
前端 | **Taro + React**（编译到微信小程序） | 一套代码同时出 H5 和小程序，方便先在浏览器验证体验 | 原生小程序（性能最好但要重写）；uni-app（Vue 技术栈）
语音 | 小程序 `wx.createInnerAudioContext` + 预先合成的音频，或系统 TTS | 听写题必需 | 第三方 TTS API（有成本）
数据看板 | 云函数聚合 + 小程序 Canvas | 周报图必须客户端画 | —

**迁移留口原则**：所有数据库读写只能出现在 `cloud/` 目录里，页面和 service 层不得直接调 `db.collection()`。这样将来迁到自建后端，只需要重写这一层。

## 三、项目结构

```
word-coach/
├─ client/                      # Taro 前端
│  ├─ src/
│  │  ├─ pages/
│  │  │  ├─ index/              # 今日任务（首页）
│  │  │  ├─ study/              # 学习卡（上滑/下滑/自动揭晓）
│  │  │  ├─ quiz/               # 抽查（交卷制）
│  │  │  ├─ stats/              # 数据看板 + 错词本
│  │  │  ├─ report/             # 周报卡片 + 分享
│  │  │  └─ me/                 # 设置、会员、押金
│  │  ├─ components/
│  │  │  ├─ WordCard/           # 学习卡（含手势）
│  │  │  ├─ Keyboard/           # 自绘字母键盘（拼写题必需）
│  │  │  └─ RingProgress/
│  │  ├─ store/                 # 本地缓存词库 + 会话状态
│  │  ├─ api/                   # 只在这里调云函数
│  │  └─ utils/
│  └─ project.config.json
├─ cloud/                       # 云函数（一个函数一个目录）
│  └─ functions/
│     ├─ task/                  # 今日任务组装（幂等）
│     ├─ review/                # 复习反馈提交（幂等）+ SRS 状态机
│     ├─ quiz/                  # 出题（不含答案）/ 交卷判分
│     ├─ report/                # 周报数据聚合
│     ├─ user/                  # 登录、初始化用户
│     ├─ class/                 # 教练端：布置任务、学员进度、催学文本
│     └─ pay/                   # 下单、支付回调、会员与押金账本
├─ shared/                      # 前后端共用：词库 JSON、常量、校验函数
└─ docs/
```

**为什么按业务域拆云函数而不是一个总入口**：云函数按调用次数和资源计费，拆开后每个函数只加载自己需要的代码，冷启动更小；也便于单独限流和排查。

## 五、接口契约

### 表 |
云函数 | 动作 | 入参 | 返回 | 必须保证
`user` | login | — | user 对象 | 首次调用自动建用户（不强制手机号）
`task` | today | date | 任务快照 + 到期词列表 | **幂等**：同日多次调用返回同一快照
`review` | submit | word_id, feedback, mode, duration_ms | 该词新状态 + 下次复习时间 | **幂等**：带 `client_req_id`，重试不重复计数
`quiz` | generate | count, source | 题目列表（**不含答案**） | 答案绝不下发
`quiz` | submit | session_id, answers[] | 总分 + 逐题对错 + 错词 | 服务端判分；错词写入次日任务
`report` | weekly | week | 周报数据 + 卡片渲染参数 | 卡片图在客户端 Canvas 生成
`class` | assign / students / nudge | … | … | 催学只生成文本，不做推送
`pay` | createOrder / onPaid | … | … | 回调必须验签 + 幂等

## 六、偷不得懒的六条规范

1. **答案不下发客户端。** `quiz.generate` 只返回题目；判分在 `quiz.submit` 里做。否则用户看一眼返回包就能全对，"抽查"这个产品就不存在了。
2. **所有提交类接口幂等。** 客户端传 `client_req_id`（uuid），服务端先查再写。碎片网络下重试是常态，重复计数会让 SRS 状态彻底错乱。
3. **时区。** 云函数运行环境是 UTC，"今天"必须显式按 **UTC+8** 计算，否则晚上 8 点之后用户的任务会被算到第二天，跨天边界必然出 bug。统一用一个 `getLocalDate()` 工具，禁止散落 `new Date()`。
4. **任务快照冻结。** `daily_tasks` 一旦生成当天不再变，避免用户中途改设置导致列表跳动。
5. **列表查询必须分页 + 限制字段。** 云开发数据库单次查询有条数上限，`words` 全量拉取会失败；词库走 CDN/云存储按需加载。
6. **不要用统计接口做高频计数。** `count()` 在数据量大时很慢且有配额，看板类数字应冗余在主文档上（如 `users.stats_cache`），定时任务刷新。

## 八、分批实施顺序（按优先级，不要并行）

### 表 |
批次 | 内容 | 交付判据 | 预估
0 | 云环境 + 登录 + 词库导入 + 骨架 | 小程序能拉到一个词并显示 | 1–2 天
1 | 学习核心：SRS 排程、反馈提交、今日任务 | 三种反馈都能正确改变下次复习时间，且跨天不炸 | 4–5 天
2 | 抽查：三种题型、自绘键盘、服务端判分、错词回流 | 交卷后逐题对错正确，错词次日必现 | 4–5 天
3 | 数据看板：打卡、掌握率、错词本、周报卡片 | 周报图可保存/分享 | 3 天
4 | 教练端：布置任务、学员进度、催学文本 | 布置后学员首页出现任务卡片 | 2–3 天
5 | 支付：会员、押金、订单与回调 | 沙箱支付走通，回调幂等 | 3–5 天
6 | 合规与打磨：隐私协议、真实设备测试、性能 | 审核通过 | 3 天

**第 0–2 批做完就有一个能给人看的东西了（约 10 个工作日）。** 建议在这个节点找 5 个真实用户试用，再决定第 3 批之后怎么做——不要一口气做到支付。
