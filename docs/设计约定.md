# 设计约定（开发前必须共识）

这份文档记录"不能靠代码审查发现的错误"——也就是那些一旦违反、上线后很久才会暴露、且很难回滚的约定。

## 一、产品层面的三条底线

1. **核心学习功能永久免费。** 词库、学习卡、遗忘曲线排程、错词本、抽查判分 —— 这些不设付费墙。
   付费只卖：周报卡片、订阅提醒、成长曲线、去广告、押金激励、人工点评加购。
   *理由：免费竞品已经把学习功能做到很好，把学习功能收费等于自断获客。*
2. **抽查的判定权在服务端；客户端只拿"当场反馈"用的答案。**
   原题约定是"答案绝不下发客户端"，2026-10-04 起改为：**出题接口可以随题下发正确答案，仅用于逐题即时反馈**（答错当场给正确释义），
   但**报告与 SRS 结论仍由服务端在交卷时重算并落库**，客户端的即时判定不作为任何数据来源。
   *改这条的理由（已付代价才改的）：纯交卷制下，学生选错之后一路错到底，错的那些秒里他记住的是"我选的那个"，
   错误印象反而被巩固了一遍；当场纠正才是加深学习，而流程不打断（1.8 秒后自动继续），报告与错词回流照旧。*
   *仍然不能让步的部分：客户端的自判结果不得回写 SRS、不得影响报告——想作弊只能骗自己，
   骗不了给家长看的那份报告，因为那份是服务端算的。*
3. **不做"每天自动推送提醒"的产品承诺。** 微信订阅消息需要用户主动授权、一次性订阅通常只能发一条。
   提醒方案 = 订阅消息（用户授权时）+ 站内待办 + 由教练/家长在群里人工催。
   *理由：这是平台限制，不是技术选择；如果在需求文档里承诺了，验收时永远不通过。*

## 二、会造成数据错乱的四条约定

1. **时区统一 UTC+8。** 云函数运行在 UTC 环境。所有"今天/本月"的判断必须走统一工具函数 `getLocalDate()` / `getLocalDayStart()`，禁止业务代码里散着 `new Date()` 直接比较。
   *不这样做的后果：晚上 8 点后用户的任务被算到第二天，跨天边界必出 bug，且只在特定时段复现，极难排查。*
2. **提交类接口全部幂等。** 客户端生成 `client_req_id`（uuid），服务端"先查后写"。复习反馈、抽查交卷、打卡三条路径都必须走这个模式。
   *不这样做的后果：碎片网络下重试导致 SRS 档位跳动、打卡天数虚增，而用户会认为是产品在骗他。*
3. **每日任务冻结快照。** `daily_tasks` 当天生成后不再变化，即使中间改了设置。次日重新组装。
   *不这样做的后果：用户学到一半，列表突然变短或变长，信任感直接崩。*
4. **`user_word_state` 必须有唯一索引 `(user_id, word_id)`。** 并发的两次反馈可能写出两条记录，之后 SRS 计算会随机取到其中一条，表现为"这个词的状态时好时坏"。
   *这类 bug 极难复现，必须在数据库层堵住。*

## 三、内容与合规

1. **词库版权**：单词表本身通常不受版权保护，但**释义文字、例句、发音音频是受保护的作品**，不能抓取商业词典或竞品内容。只使用自撰或已授权内容。这是法律风险，不是技术问题。
2. **未成年人信息**：只采集学习必需数据（学习记录、必要标识），不采集通讯录、位置、相册；不设 UGC 社区；隐私指引里写明用途与保存期限。
3. **押金的合规前提（未满足就不要上线该功能）**：
   - 仅限成年人（实名验证）
   - 上限 99 元，档位 30 / 50
   - 由持牌第三方存管，不进经营账户
   - 达标**全额返还**；未达标转为次月会员余额，**不做"平台留存款"**
   - 条款写清达标条件（以"每周到课天数 + 抽查参与率"为准，**不以随机抽查的正确率为准**）
4. **支付**：个人主体小程序不能用微信支付。收钱必须有企业/个体工商户主体 + 商户号。
5. **服务类目**：教育类目可能要求资质，按要求核实后选择；如不满足，评估以"工具"类目申报的可行性与风险。

## 四、性能与成本约定

1. **词库不打包进小程序主体。** 放云存储/CDN，按当前学习范围分片加载，本地缓存。小程序有包体积上限，全量词库一定会超。
2. **看板数字不要实时 `count()`。** 用冗余字段 + 定时聚合。
3. **`review_logs` 与 `quiz_items` 要设保留策略**（例如明细保留 90 天，之后只留聚合），否则表单会无限膨胀、查询变慢、成本上升。
4. **云函数要拆域**，不要写一个总入口函数：按业务域拆开后冷启动更小，也便于单独限流和排查。

## 五、上线前自查清单

- [ ] 抽查交卷时服务端**重算**判分与 SRS（客户端的逐题自判回传结果不采信、不落库）
- [ ] 复习提交 / 抽查交卷 / 打卡 三条路径都做了幂等测试（同一 `client_req_id` 重复提交）
- [ ] 跨天测试：把设备时间调到 23:59 与 00:01 各学一次，检查任务与打卡归属是否正确
- [ ] `user_word_state` 与 `daily_tasks`、`checkin_records`、`orders` 的唯一索引已建
- [ ] 用户隐私保护指引、用户协议已填写并提交
- [ ] 押金与会员条款写清了达标条件、退还方式、处理周期
- [ ] 真实设备（至少一台 iOS、一台 Android）跑通完整闭环
- [ ] 词库内容来源可追溯（自撰 / 已授权），并能提供说明

## 六、界面色彩规范（皮肤系统 1.2.0）

> 2026-10-23 起生效。背景：改造前全站 **423 处硬编码颜色、107 种色值、0 处 CSS 变量**，
> 任何换肤都无从下手。现已完成第一步变量化（233 处 → 24 个 token），本节是后续所有界面改动的依据。

### 6.1 Token 分层（唯一的取色入口）

| 层 | token | 夜色取值 | 用途 |
|---|---|---|---|
| 页面底 | `--bg` / `--bg2` | `#0f1620` / `#101a24` | 页面背景、整块抬高层 |
| 卡面 | `--surface` `--surface2` `--surface3` | `#18222e` `#1e2a38` `#243040` | 卡片 / 卡内嵌套块 / 键盘按键面 |
| 填充 | `--fill` `--fill2` `--fill3` | `#16202c` `#16222f` `#141d28` | 输入框、行底、核对列表行 |
| 线 | `--line` ~ `--line6` | `#2b3949` 系 | 描边与分割线（由主到次） |
| 文字 | `--text` `--text2` `--text3` | `#e8eef5` `#e8f0f8` `#cfe0f0` | 主/次/三级文字 |
| 弱化 | `--muted` ~ `--muted5` | `#8fa3b7` 系 | 说明文字，逐级减弱 |
| 强调 | `--accent` | `#3ea6ff` | 链接、主按钮、选中态 |
| 按下 | `--active` | `#3a4a5e` | 瞬时按压反馈 |

### 6.2 三条硬规则（测试会拦，别赌）

1. **结构色必须走 token。** 业务 wxss 里禁止再出现 token 对应的原始色值；
   `tests/theme.test.js` 全库扫描，写回去就红。
2. **功能色五色固定，永不随皮肤：** 对 `#2fd07a` / 错 `#ff5c72` / 警示 `#ffb020` /
   金币 `#ffd166` / 主题紫 `#7c5cff`。对错语义跟着皮肤变，用户会看不懂反馈。
3. **新增皮肤必须过对比度门槛**（`scripts/check-contrast.js`，WCAG 2.1）：
   正文与强调文字 ≥ **4.5:1**；弱化说明文字 ≥ **3:1**（它不承担关键信息）；
   描边/分割线 vs 卡片 ≥ **1.5:1**（仅约束新皮肤；夜色的弱描边是既有设计，豁免）。

### 6.3 首发五套皮肤与解锁

**入口在「设置」页**（底栏第三个 tab）。2026-10-23 起底栏由四个 tab 缩为三个
（今日 / 背词 / 设置）：「数据」「班级」是低频管理动作，连同皮肤一起收进设置页，
高频动作留在手指够得着的地方。不叫「我的」是因为没有登录态，叫「我的」会让人以为有账号体系。

![五套皮肤预览](assets/皮肤预览-五套.png)

| 皮肤 | id | 解锁 | 定位 |
|---|---|---|---|
| 夜色 | `night` | 免费 | 默认深色，晚上背词不刺眼 |
| 樱粉 | `sakura` | 免费 | 白天暖调，争取让最多人用上 |
| 蜜橘 | `honey` | 完成 5 次任务 | 成长层 |
| 薄荷 | `mint` | 完成 7 次任务 | 成长层 |
| 晴空 | `sky` | `paid` 预留 | 个人主体无虚拟支付通道，代码先占位 |

*蔷薇（rose）曾被列为第二套粉色，与樱粉并排几乎分辨不出，已移除。
后续加皮肤的原则：**浅色之间必须拉得开家族差异**（粉/橘/绿/蓝），宁可少一套也不要两套看着一样。*

*合规背景：微信「虚拟支付」要求企业主体 + 类目资质，个人主体无入口；iOS 端虚拟物品必须走
Apple IAP，小程序内无此通道。所以「付费皮肤」在主体变更前只是占位，不写购买流程。*

### 6.4 新增皮肤的标准动作（五步）

1. `utils/theme.js` 的 `SKINS` 里加一项：id、名称、desc、unlock、tokens（只写与夜色的差异键，
   未写出的键自动继承夜色——浅色皮肤建议全写，别赌继承）。
2. `node scripts/check-contrast.js` —— 有 ✗ 就回调色值，直到全 ✓。
3. `node scripts/gen-theme-wxss.js` 重新生成 `theme.wxss`
   —— **这个文件是生成出来的，不要手改**；tests ①d 会校验它与 theme.js 一致。
4. `tests/theme.test.js` 跑绿（token 对齐 + 无残留硬编码 + 对比度全过）。
5. 设置页不用改：皮肤卡是按 `theme.SKINS` 循环渲染的，加进清单就自动出现。

### 6.5 命名分层（避免「叫马卡龙结果是纯色」的预期落差）

- **1.2.0 扁平层**用颜色名：夜色 / 樱粉 / 蔷薇 / 蜜橘 / 薄荷 / 晴空。
- **1.3.0 拟物付费层**才用甜点名（糖霜马卡龙、甜甜圈、焦糖布丁、草莓牛奶），
  配得上名字的质感再做：CSS 轻拟物（双层 box-shadow 内高光 + 大圆角）为主，
  少量装饰 png（每套 3~5 张、单张 <200KB），**不做全图切图**（每套 +2~3MB 不可接受）。
  参考图：[assets/拟物参考-扁平vs糖果.png](assets/拟物参考-扁平vs糖果.png)

### 6.6 已知边界（浅色上线前必须清完）

变量化替换了 233 处，剩余约 **190 处硬编码**是一次性语义浅色底与 rgba 遮罩
（照片遮罩 `rgba(15,22,32,.55)`、底部固定条深底、坏词行 `rgba(255,92,108,.10)` 等）。
深色皮肤下它们没问题；**浅色皮肤上线前逐页过一遍**，该 token 化的 token 化，
该改成半透明黑/白的改掉，否则浅色下会出现「深色孤岛」。
